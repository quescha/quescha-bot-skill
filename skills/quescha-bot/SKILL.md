Создай или измени бота Quescha по запросу: $request

Определи папку установленного skill. В Kimi Code её обозначает `${KIMI_SKILL_DIR}`; в других агентах используй фактическую папку, из которой загружен этот `SKILL.md`. Все команды ниже выполняются локально. Не запрашивай API Quescha, логин, пароль, токен аккаунта или ключи интеграций.

## Обязательный рабочий цикл

1. Прочитай `references/traps.md`, `references/generation-guide.md`, `references/format.md` и `references/checks.md`. Журнал `traps.md` обязателен: подбери похожие ошибки заранее и добавь проверки до длинных прогонов. При сопровождении skill пополняй этот единый журнал каждой новой ошибкой с причиной, решением и регрессией, не создавай параллельные журналы. Затем используй **полную** инструкцию, соответствующую языку пользователя: `references/genbot_instructions_ru_max.txt` или `references/genbot_instructions_en_max.txt`. Это нормативное руководство по блокам, действиям, интеграциям и типовым ловушкам; краткие памятки его не заменяют. Не читай обе языковые версии без необходимости.
2. Если пользователь дал существующий ZIP, сначала сохрани исходный архив и распакуй его в новую рабочую папку:

   ```bash
   node "${KIMI_SKILL_DIR}/bin/quescha-bot.js" unpack existing-bot.zip my-bot --json
   ```

   Если ZIP не поддерживается локальным чтением, попроси пользователя экспортировать проект заново, а не извлекай файлы небезопасным способом.

3. Для нового бота создай отдельную папку:

   ```bash
   node "${KIMI_SKILL_DIR}/bin/quescha-bot.js" init my-bot --name "Название бота" --json
   ```

4. Спроектируй путь клиента целиком до правки: проект, цепочки, блоки, кнопки, списки, глобальные переменные, сценарии действий и приложения. Не ограничивай результат визиткой, если запрошены записи, заказы, роли, расчёты или интеграции. Задавай уточняющий вопрос только если без ответа нельзя выбрать логику; остальные разумные допущения перечисли в итоге.
5. Редактируй `bot.json` в рабочей папке, а не установленные файлы skill. Сохраняй существующие ID и данные при изменении бота. Все вложенные структуры, которые формат хранит строкой, должны остаться JSON-строками.
6. Для сценариев действий создай `external.code.js` рядом с `bot.json`: используй `await scenario(...)` и `qb.step(...)` с настройками `qb.cfg.*` из полной max-инструкции. CLI скомпилирует их при `check`, `test`, `mutate` и `build`. Не вставляй исходный `scenario/qb` внутрь JSON-строки `external.actions` и не редактируй сгенерированные действия вручную, если есть `external.code.js`. Образец сложного бота — `assets/examples/booking/`.
7. Обнови `dryrun.js`: задай реалистичные `jsstore`/`cases` для JS-действий и `need` для обязательных возможностей. Полный dry-run входит в `check`; его ошибки и неразрешённые замечания блокируют сборку.
8. Обнови `tests.js`: проверяй бизнес-инварианты, расчёты, роли, обязательные настройки и критические пути, а не только синтаксис. Тест получает объект бота и `assert` из `node:assert/strict`; он не запускает runtime Quescha.
9. Перед полными мутациями сделай раннюю smoke-проверку критического пути: ввод → изменение строки → повторное чтение → решение → результат. Проверь U+2060, значения, похожие на арифметическое выражение, версии и роли. Если проект предоставляет настоящий runtime Quescha, сначала выполни короткий `stend-smoke.js` с автоматическим обходом; полный стенд всё равно обязателен. В публичном CLI runtime нет, поэтому локальная smoke-проверка не заменяет диалог после импорта. Каждую новую ошибку с решением и регрессией вноси в `references/traps.md`. Затем обнови `mutations.js`: добавь как минимум одну реалистичную поломку для каждого критического инварианта. Мутация обязана ловиться проверкой или смысловым тестом.
10. Выполни полный цикл:

    ```bash
    node "${KIMI_SKILL_DIR}/bin/quescha-bot.js" check my-bot --json
    node "${KIMI_SKILL_DIR}/bin/quescha-bot.js" test my-bot --json
    node "${KIMI_SKILL_DIR}/bin/quescha-bot.js" mutate my-bot --json
    node "${KIMI_SKILL_DIR}/bin/quescha-bot.js" build my-bot --json
    ```

    Норма: 0 ошибок, 0 неразрешённых замечаний, все тесты зелёные, 0 пропущенных мутаций. Не выдавай архив, если `build` завершился ошибкой.
11. Проверь фактический архив:

    ```bash
    node "${KIMI_SKILL_DIR}/bin/quescha-bot.js" inspect my-bot/dist/<slug>.zip --json
    ```

12. В ответе дай пользователю точный путь к ZIP и кратко перечисли: что умеет бот, результаты проверок, принятые допущения и что настроить после импорта. Не называй локальные проверки тестом настоящего движка.

## Правила содержимого

- Язык сообщений и названий — язык описания пользователя; системные имена полей и шаблонов не переводи.
- У цепочки должен быть способ запуска. Все блоки одного интерактивного сценария лежат в одном `messages[].message`.
- ID блока — 8 латинских букв или цифр; переходы блоков — `{label,value}`; кнопки сценариев действий ссылаются на блок строкой.
- Не оставляй незаполненные обязательные настройки. Секреты не вшивай: используй явные placeholders и объясни настройку в аккаунте.
- Для запуска сразу после добавления интеграции ставь в действие `first: true` рядом с `name`; в готовом боте допускается `first: true` внутри заглушки `name`. Для Яндекс Метрики используй `metrikafirst: true`. Runtime выберет первую активную интеграцию по `ordernumber` и `id`. Сам объект `name` сохраняй. Если нужна конкретная интеграция по ID, флаг не ставь.
- На блок `acceptpayment:true` не должно быть входящих переходов.
- Не создавай мгновенные циклы напоминаний и не накладывай блоки друг на друга.
- Вложения складывай только в `upload/` рабочей папки. Не добавляй туда `.env`, ключи, пароли, персональные данные или посторонние исходники.

## Граница проверки

CLI компилирует `scenario/qb`, выполняет статический анализ и полный dry-run (включая JS с тестовыми данными), пользовательские тесты и мутации, но не содержит серверный runtime Quescha. Окончательный сценарий: пользователь загружает ZIP в «Настройки аккаунта» → «Экспорт / Импорт», выбирает каналы, настраивает свои интеграции и проверяет диалог в мессенджере. Сообщи об этой границе явно.
