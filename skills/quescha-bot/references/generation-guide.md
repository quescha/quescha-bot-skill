# Руководство по генерации бота для публичного CLI

Цель — не красивый JSON, а бот с полным путём клиента, проверенными инвариантами и архивом для штатного импорта.

## 1. Спроектируй до редактирования

Зафиксируй в рабочих заметках:

- кто пользователи: клиент, сотрудник, администратор;
- точку входа и команды;
- каждый экран, ответ и переход;
- где хранятся данные и какие записи нельзя дублировать;
- какие значения являются настройками владельца;
- ошибки ввода, пустые результаты, отмену и повторное нажатие;
- интеграции, которые владелец подключит после импорта;
- измеримый результат: заявка, запись, заказ, оплата, ответ или отчёт.

Не добавляй приложение, нейросеть или интеграцию только ради сложности. Для выбора из нескольких вариантов достаточно кнопок; одну настройку храни глобальной переменной, таблицу однотипных строк — списком.

## 2. Используй существующий формат

Новый бот начинается с `init`, существующий — с `unpack`. Не меняй структуру записей произвольно: используй полный шаблон и сохраняй незнакомые поля.

Сначала задай числовые ID проектов, цепочек, шагов, списков, строк, переменных, сценариев и приложений. Затем создавай блоки со строковыми ID. Не переиспользуй один ID для разных сущностей внутри массива.

При изменении существующего бота:

- не перенумеровывай без необходимости;
- не удаляй `listdata`, если пользователь не попросил очистить данные;
- не заменяй рабочий архив — собирай новый в `dist/`;
- сохраняй дополнительные поля записей, даже если схема их не описывает.

## 3. Собери связный диалог

- Стартовый блок имеет `order:0`.
- Каждая кнопка ведёт в существующий блок того же шага или выполняет понятное URL/системное действие.
- У каждого вопроса есть путь при правильном и неправильном ответе, отмена и возврат.
- Не оставляй недостижимые блоки и сценарии без причины.
- Все сообщения, имена кнопок, списков и настроек — на языке пользователя.
- Подстановки и системные литералы не переводи.
- Экран, который возвращается сам на себя и показывает новое состояние, должен заменять предыдущее сообщение соответствующими настройками кнопок; не создавай ленту одинаковых рабочих экранов.

## 4. Данные и настройки

- Одиночная настройка: `global`, чтение `#{g_Имя}`.
- Таблица: `lists` + начальные `listdata`.
- Личные данные подписчика: поля строки с отбором по `ClientID`; не показывай чужие записи.
- Автополя `ClientID`, `Messenger`, `BotID`, `CreationDate` сохраняй в `headers` и значениях строк.
- Значение, которое должен ввести владелец, оформляй понятным placeholder и перечисляй в итоговой инструкции.
- Не вшивай реальные токены, пароли, приватные ключи, JWT и персональные данные.

## 5. Сценарии действий

Исходник сценариев — `external.code.js` рядом с `bot.json`. Используй `await scenario(...)`, `qb.step(...)` и `qb.cfg.*` по полной max-инструкции для языка пользователя. При каждом `check`, `test`, `mutate` и `build` локальный компилятор обновляет `external[].actions` в памяти; в итоговый ZIP попадает только готовый JSON действий. Не записывай исходный `scenario/qb` в JSON-строку `actions`.

Полный рабочий образец — `assets/examples/booking/external.code.js`. Он показывает чтение справочника, получение цены из выбранной строки, запись данных, JS-действие, ветки и вывод только своих записей. Для кнопки `nextmessage` её поле `data` читается в сценарии как `[Data1]`, а не как `answervar` блока.

При создании или переносе действия:

1. Используй сборщики и полные формы настроек из max-инструкции; не выдумывай поля.
2. Обнови ссылки по именам списков/сценариев и строковым ID блоков.
3. Проверь, что ветка «иначе» и выход реально настроены.
4. Не полагайся на незаполненную переменную: сначала определи шаг, который её пишет.
5. Числа сравнивай как числа в коде, а не полагайся на лексикографический порядок строк.
6. Настрой `dryrun.js`: передай реалистичные `jsstore`, дополнительные `cases` и обязательные возможности в `need`. Dry-run выполняет JS с этими данными и проверяет настройки, но не моделирует серверный диалог и реальные интеграции.
7. Покрой критические поля и формулы отдельными пользовательскими тестами, а поведение проверь после импорта.

При изменении старого экспорта без `external.code.js` готовый JSON в `external[].actions` сохраняется. Новые сценарии добавляй через `external.code.js`; не переписывай вручную действия, если такой исходник уже есть.

## 6. Платежи, время и приложения

- Ссылку на оплату и подтверждение платежа разделяй. На блок `acceptpayment:true` не ведут обычные переходы и кнопки.
- Круг напоминаний требует задержки; мгновенный молчащий цикл запрещён.
- Для отложенных действий проверяй, что нужные данные доступны в момент срабатывания, а не только в исходной ветке.
- Каталог товаров — WebApp `cat`, запись — `cal`, специальная интерактивная форма — `miniapp`, если они действительно нужны.
- Внешние цены и суммы из приложения перепроверяй логикой бота; не считай клиентский ввод доверенным.

## 7. Тесты

`tests.js` экспортирует массив:

```js
module.exports = [
  {
    name: 'Цена записи равна цене выбранной услуги',
    run (bot, assert) {
      // прочитай нужные блоки/списки/действия и проверь инвариант
    }
  }
]
```

Тесты работают с JSON-снимком. Для чистой формулы можно вынести её в отдельный локальный модуль рабочей папки и проверить границы, ноль, дробные значения, большие числа и ошибочный ввод. Не импортируй в тест серверные модули Quescha.

Обязательно проверь:

- главный путь и возврат в меню;
- обязательные настройки;
- деньги, даты, остатки и права, если они есть;
- защиту от дублей и повторного исполнения;
- пустые данные и ошибку внешнего шага;
- отсутствие секретов и чужих адресов.

## 8. Мутации

Мутация намеренно ломает один инвариант:

```js
module.exports = [
  {
    name: 'Кнопка оплаты ведёт на блок приёма платежа',
    expect: 'E_PAYMENT_INCOMING',
    mutate (bot) {
      // меняй только копию bot, которую передаёт CLI
    }
  }
]
```

Если `expect` задан, валидатор должен вернуть этот код. Без `expect` поломку может поймать смысловой тест. Поломка, которую ничто не поймало, блокирует `build`.

Мутируй реальные риски: удалённое условие отбора, чужой `ClientID`, пропущенное списание остатка, повторное исполнение, пустая настройка, неверная ссылка. Не ограничивайся синтаксическими поломками.

## 9. Сдача

Запусти отдельно check/test/mutate, затем build и inspect фактического ZIP. Исправь ошибки и разбери каждое замечание. В итоге укажи:

- путь к архиву;
- состав и поведение бота;
- число тестов и пойманных мутаций;
- допущения;
- настройки после импорта;
- границу локальной проверки и необходимость диалогового теста в аккаунте.
