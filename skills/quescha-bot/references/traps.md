# Ловушки генерации ботов: ошибки, решения и предупреждение повторов

Единый постоянно пополняемый журнал ошибок сборки и проверки готовых ботов. Не заменяет
`genbot_instructions_*`, `ПРАВИЛА-ГОТОВЫХ-БОТОВ.md` и `ЖУРНАЛ-ДОРАБОТОК.md`: здесь фиксируется
практический путь от симптома до регрессионной проверки.

## Обязательный порядок перед новым ботом

1. Прочитать этот файл и подобрать существующие проверки для каждого похожего узла. Не копировать
   предметную логику прошлого бота без проверки её предположений.
2. До сборки выписать все операции записи: поле, тип, источник, возможные U+2060 и значения,
   похожие на арифметическое выражение. Для каждой роли выписать доступные ей записи.
3. После `check.js` и быстрых смысловых тестов сначала запустить короткий `stend-smoke.js`:
   ввод → изменение строки → повторное чтение сырых данных → решение → запись результата →
   автоматический обход. Только затем запускать полный `mutations.js`. Полный `stend-ok.js`
   остаётся обязательным после мутаций и регистрации карточки.
4. После любой ошибки сначала записать её в этот файл, затем добавить регрессию в `test-*.js`
   и/или `mutations.js` и проверку сырых данных в стенд. Исправление без такой записи и проверки
   не считается завершённым.
5. Полные мутации и стенд запускать после финального изменения артефакта. Не перезапускать их,
   если изменился только сам тест или документация; не утверждать результат до фактического завершения.

## Шаблон новой записи

Новые ошибки добавлять в начало следующего раздела, не удаляя прежние.

```markdown
### ГГГГ-ММ-ДД — Краткая суть

- **Этап:** dry-run / смысловой тест / мутация / smoke / полный стенд / инспектор.
- **Симптом:** что именно сломалось у пользователя или в проверке.
- **Причина:** подтверждённый механизм, а не предположение.
- **Решение:** файлы и конкретное изменение.
- **Регрессия:** тест, мутация и стенд, которые теперь ловят ошибку.
- **Перед следующим ботом:** что проверить заранее.
```

## 2026-11-28 — Сборщики QB отбрасывали first при формировании действия

- **Этап:** проверка экспорта нейросети через `qb.cfg.*`.
- **Симптом:** runtime понимал `first`, но `qbcfg.ref` возвращал только `label` и `value`,
  а шаблоны `qbdefaults` не знали `first`. Сгенерированный флаг исчезал или сборка падала.
- **Причина:** проверка началась только с интерфейса и runtime и не охватывала компилятор
  сценариев, через который нейросеть формирует JSON.
- **Решение:** `qbcfg.ref` сохраняет `first`; `qbdefaults` допускает его в payment, CRM,
  Google Sheets/Drive и Яндекс Диске, `crmlink.emptyCondition` — `metrikafirst`.
- **Регрессия:** `backend/test-integration-first-qb.js` проверяет сохранение `first` и
  `name.first` во всех сборщиках и condition. Пул БД закрывается явно.
- **Перед следующим ботом:** любое новое поле действия проверять по цепочке
  UI → `qbcfg.ref` → `qbdefaults` → экспорт → runtime → установщик готового бота.

## 2026-11-28 — Тест без закрытия БД блокирует следующие проверки

- **Этап:** запуск backend-теста и ESLint одной цепочкой `node test && eslint`.
- **Симптом:** тест напечатал успех, но команда не завершалась, а следующий за `&&` ESLint
  вообще не запускался. Это уже повторная ошибка диагностики и завершения тестового процесса.
- **Причина:** импорт `src/models` открыл пул Sequelize, а тест не закрыл подключение.
  Принудительный `process.exit(0)` маскирует проблему ресурсов, поэтому правильное решение —
  закрыть пул явно и на успешном, и на ошибочном пути.
- **Решение:** `backend/test-integration-first.js` вызывает `await sequelize.close()` после
  успеха и после ошибки. Больше не диагностировать «завис ESLint», не проверив, какая команда
  фактически зависла и была ли запущена следующая.
- **Регрессия:** тест завершается сам, затем ESLint стартует и проверяет изменённые файлы.
- **Перед следующим ботом:** после каждого теста проверять код возврата процесса, а не только
  вывод. Для БД закрывать соединения в `finally`/обоих ветках. Разделять подтверждённый успех
  теста и подтверждённый запуск следующего шага.

## 2026-11-28 — Выбор первой интеграции не должен зависеть от name

- **Этап:** проверка крайнего случая при добавлении `first` в действия интеграций.
- **Симптом:** галочка первой интеграции работала только при заполненном `name`; при `name: null`
  платёж, Google Sheets/Drive, Яндекс Диск, Метрика и CRM выходили раньше выбора первой записи.
- **Причина:** старые ранние выходы `name === null` и условия веток проверяли наличие объекта,
  но не флаг `first`/`metrikafirst`.
- **Решение:** ранние выходы разрешены только при отсутствии и `name`, и флага. Runtime выбирает
  первую активную запись по `ordernumber` и `id`; без флага сохраняется конкретный ID.
- **Регрессия:** `backend/test-integration-first.js` проверяет `first` и `name.first`, null,
  конкретный ID и сохранение флага установщиком. Оба Vue-редактора проходят ESLint.
- **Перед следующим ботом:** для каждого нового флага проверять три состояния: нет флага,
  флаг с заполненным объектом, флаг с `null`. Не полагаться на главный путь.

## 2026-11-28 — Публичный skill не был синхронизирован после изменения процесса

- **Этап:** проверка связанности локальной разработки и `quescha-bot-skill` для других агентов.
- **Симптом:** локальный журнал ловушек и ранний smoke существовали, но в публичном `SKILL.md` их не было.
- **Причина:** правило синхронизации явно срабатывало только после правки четырёх
  `genbot_instructions_*` и не покрывало изменение самого процесса разработки.
- **Решение:** добавлены публичный `references/traps.md`, инструкции по ранней smoke-проверке,
  копирование журнала в `sync-public-skill.js` и `test/process-docs.test.js`. Публичная граница
  без runtime явно отделена от стенда настоящего движка. Правило теперь требует синхронизацию
  после изменения любого этапа процесса или журнала ловушек, а не только инструкций генерации.
- **Регрессия:** `npm run check` в `quescha-bot-skill/` — 42/42, включая наличие журнала,
  обязательное чтение в `SKILL.md`, раннюю smoke-проверку, регрессии, границу публичного CLI,
  аудит секретов и автономную сборку без репозитория.
- **Перед следующим ботом:** после изменения локального процесса сразу запускать синхронизатор
  и проверки публичного пакета, перечислять файлы для GitHub, не ограничивать связанность max-файлами.

## 2026-11-28 — Запись ISO-даты вычислялась как арифметика

- **Этап:** полный стенд после принятия и завершения наряда.
- **Симптом:** после завершения актив выпадал из последующих планов. Сырое `ListData.data`
  содержало `"ПоследнееТО":"1987"` вместо `2026-11-28`.
- **Причина:** движок вычислил строку `2026-11-28` как `2026 - 11 - 28`. Такое значение нельзя
  записывать в поле списка без защиты.
- **Решение:** в `agent_remont_aktiva/external.code.js` дата перед записью проходит через
  `рмБезопасно`, добавляющий U+2060 и не позволяющий вычислителю распознать выражение.
- **Регрессия:** `test-ok.js` проверяет U+2060 и обратный разбор даты; отдельная мутация
  «наряды: дата вычисляется как выражение»; диагностический стенд читает сырую строку и видит
  `⁠2026-11-28`, затем подтверждает все 3 актива в расчёте.
- **Перед следующим ботом:** искать даты, номера, телефоны и дроби, которые состоят только из цифр
  и знаков `+ - * / % ( ) . ,`. Проверять запись сырого значения, а не только текст сообщения.

## 2026-11-28 — U+2060 отключал обновлённый актив

- **Этап:** первый полный стенд после ввода наработки в MAX.
- **Симптом:** сразу после корректного увеличения наработки актив исчезал из расчёта, а последующие
  отказы не записывались. На очищенном выводе поля выглядели правильными.
- **Причина:** `рмБезопасно('1000')` добавляло U+2060 перед числом. Нормализаторы `рмЦелое` и
  `рмДробное` проверяли исходную строку регулярным выражением и не снимали этот символ.
- **Решение:** `рмЧисло`, `рмЦелое` и `рмДробное` в `agent_remont_aktiva/formula.js` теперь сначала
  вызывают `рмПоле`, которое удаляет служебные символы.
- **Регрессия:** тест с `⁠1000` и `⁠2` в числовых полях, отдельная мутация
  «формула: невидимый символ ломает число», стенд повторяет ввод и последующие события.
- **Перед следующим ботом:** каждое число, пришедшее из `listRead`, нормализовать так же, как текст.
  Проверять не только начальные строки, но и повторное чтение после `listAdd`/`listEdit`.

## 2026-11-28 — Час автоматического обхода брался из неправильной шкалы

- **Этап:** проверка ежедневного плана в полном стенде.
- **Симптом:** ручные планы работали, автоматический не запускался и не попадал в «Запуски».
- **Причина:** сначала тест подставил локальный час ОС, затем UTC, но слот бота вычислялся по
  `CurrentDate/CurrentTime` и формуле часового пояса. В записи подписчика фактический `дж_слот`
  отличался от обоих вариантов.
- **Решение:** в `stend-ok.js` час вычисляется той же шкалой UTC+3:
  `new Date(Date.now() + 3 * 3600000).getUTCHours()`. Изолированный обход подтвердил `автоплан`.
- **Регрессия:** полный стенд проверяет один автоматический запуск и отсутствие дубля повтором.
- **Перед следующим ботом:** сверять `дж_слот`, `CurrentDate`, `CurrentTime` и настройку часа,
  а не полагаться на `getHours()` или `getUTCHours()` операционной системы.

## 2026-11-28 — Экранирование строк внутри JS-действий

- **Этап:** первый dry-run после сборки.
- **Симптом:** «Invalid regular expression flags» и «Invalid or unexpected token»; часть сценариев
  была недостижима.
- **Причина:** в строках генератора использовались `\d`, `\s`, `\/` и `'\n'`. На следующем уровне
  JavaScript они уже превратились в `/start(s.*)?` и в настоящий перенос внутри строкового литерала.
  Отдельно метка `окна` встречалась дважды в сценарии «Меню».
- **Решение:** регулярные выражения записаны без лишних экранов (`[0-9]`, `[/]`), переносы —
  через `String.fromCharCode(10)`, повторная метка переименована.
- **Регрессия:** dry-run выполняет все 45 JS-действий, компилятор без замечаний, связность 12/12.
- **Перед следующим ботом:** оценивать строку на каждом уровне вложенности: исходник → JSON действия →
  JS движка. Не маскировать проблему удалением проверок или отключением веток.

## 2026-11-28 — Ошибки фикстур принимались за ошибки бота

- **Этап:** смысловой тест и стенд.
- **Симптом:** ложные расхождения миллисекунд, версии плана и автоматического часа; отладочная
  нейросеть не разбирала вопрос.
- **Причина:** в одном ожидании число сравнивалось со строкой; в другом версия пересчитывалась уже
  с назначенным нарядом. Отладочный обработчик JSON не снимал U+2060, хотя штатная заглушка это делает.
- **Решение:** типы фикстур приведены к runtime, версия считается на том же наборе данных, тестовый
  обработчик снимает U+2060 перед разбором. Сначала подтверждается сырьё и только потом меняется код бота.
- **Регрессия:** 502 смысловые проверки и 391/391 мутация проходят на одном зафиксированном `data.txt`.
- **Перед следующим ботом:** повторять входные данные движка, включая невидимые символы, типы массивов
  и текущие версии. Ошибку теста отличать от ошибки бота, но не менять ожидания ради зелёного результата.

## 2026-11-28 — Предупреждения инспектора не являются ошибками динамических блоков

- **Этап:** публичный `inspect` фактического ZIP.
- **Симптом:** 11 предупреждений `W_BLOCK_UNREACHABLE`.
- **Причина:** блоки запускаются динамическими кнопками `nextmessage`, которые статический инспектор
  не раскрывает.
- **Решение:** предупреждения разобраны без изменения бота: проектный dry-run подтверждает все 12
  блоков достижимыми и 0 замечаний; полный стенд проходит их по реальным командам.
- **Регрессия:** `inspect` — 0 ошибок, полный стенд — 49/49.
- **Перед следующим ботом:** каждое замечание разбирать по исполнению, не удалять «лишние» блоки
  автоматически и не считать количество предупреждений признаком неработоспособности.

## 2026-11-28 — Процесс: полные прогоны запускались до раннего стенда

- **Этап:** организация проверки.
- **Симптом:** несколько полных мутационных прогонов и полных стендов повторялись после ошибок записи.
- **Причина:** первая полная мутационная серия была запущена до того, как настоящий движок проверил
  изменённые строки и автоматический обход. Короткие диагностики делались только после длинных серий.
- **Решение:** в обязательный порядок добавлен `stend-smoke.js` между быстрыми тестами и полными
  мутациями. Он проверяет ввод, повторное чтение, решение, сырой результат и автоматический обход.
- **Регрессия:** `agent_remont_aktiva/stend-smoke.js` — 10/10 за 66 секунд: роли, ввод,
  повторное чтение, план, наряд, сырые дата и наработка, сохранение актива и обход;
  полный `stend-ok.js` — 49/49 отдельно.
- **Перед следующим ботом:** сначала маленькая проверка критического пути, затем длинные серии.
  После изменения только теста или документации повторять только затронутую проверку.

> Публичный CLI не содержит настоящий runtime Quescha. Ранняя smoke-проверка здесь — dry-run, смысловые тесты, мутации и inspect ZIP. Короткий stend-smoke.js выполняется только при наличии проектного runtime; диалог после импорта обязателен в любом случае.
